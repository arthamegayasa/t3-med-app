# T3 Med fork

T3 Med is T3 Code organised around patients instead of code projects, for one doctor on a Windows laptop. This file records what the fork changes in upstream files, so an upstream merge can be checked against it. What keeps upstream's name, what carries T3 Med's, and the routine for taking an upstream release are in [BRANDING.md](BRANDING.md). Product decisions are in the workspace repo (`arthamegayasa/t3-med`, `docs/adr/`).

## Branches and remotes

- `upstream` is `pingdotgg/t3code`. Its push URL is disabled on purpose.
- `med` is T3 Med. It started from upstream tag `v0.1.8` and now sits on **`v0.1.10`**, merged on 17 November 2026 (`v0.1.9` came with it). Upstream's `package.json` still reads `0.1.9` at that tag, so `t3 --version` prints `0.1.9`.
- Merge upstream from stable release tags, about once a month, by the routine in [BRANDING.md](BRANDING.md). Nightlies move too fast to follow.

## Building on Windows

- Check out to a path **without spaces**. The web build fails under a path such as `D:\T3 Projects\…` (`UNLOADABLE_DEPENDENCY`, os error 123), because a worker entry is resolved from a URL-encoded path.
- Install `vp` (`irm https://vite.plus/ps1 | iex`), then from the repository root: `vp i`, `vp run --filter t3 build`.
- Run the built server: `node apps/server/dist/bin.mjs serve --port 3899` with the Node that `vp` provides (Node 26). It serves the web UI on that port.
- The background service does not exist on Windows; the server runs in the foreground.
- The web client's browser tests (`*.browser.test.tsx`) need Playwright's Chromium shell once: `node apps/web/node_modules/playwright/cli.js install --only-shell chromium`. Then, in `apps/web`, `vp test run --project browser <files>`.
- `start-t3-med.cmd` in the repository root starts the built server on port 3899 with the patient workspace (`D:\T3 Projects\T3 Med`) as its project and opens the browser. Closing its window stops T3 Med.
- `build-t3-med-installer.cmd` builds the desktop app's installer; see The desktop app.

## The desktop app

T3 Med has a Windows desktop app: upstream's Electron app (`apps/desktop`) built by upstream's packaging script, with the fork's identity. `start-t3-med.cmd` still works and is the fallback.

- **Build the installer:** `build-t3-med-installer.cmd` in the repository root. It builds upstream's resource monitor with Cargo, then runs `node scripts/build-desktop-artifact.ts --platform win --target nsis --arch x64`. The installer is `release\T3-Med-<version>-x64.exe` (about 210 MB; `release/` is ignored by git). It takes about seven minutes. It rebuilds `apps/server/dist`, the tree `start-t3-med.cmd` serves, so close the browser version before building. It reads the `T3CODE_DESKTOP_*` variables and any `.env` of the shell it runs in; run it from a plain shell and pass it no arguments.
- **What the build needs:** `vp`, Python 3, Rust (`rustup`, installed per user, with the `x86_64-pc-windows-msvc` target) and the Visual Studio C++ build tools with a Windows SDK. Upstream's own preflight also demands the Spectre-mitigated MSVC libraries, which need an administrator to install and which nothing in the build uses; the script avoids that check with upstream's `T3CODE_DESKTOP_REUSE_RESOURCE_MONITOR`, the switch upstream's release workflow sets.
- **Identity** is in `scripts/lib/med-identity.ts`, read by the app through `apps/desktop/src/med/identity.ts` and by packaging through `scripts/med/desktop-package.ts`: product name `T3 Med`, app id `com.arthamegayasa.t3med`, package name `t3med`, scheme `t3med`. Nothing may equal T3 Code's value, because T3 Code is installed on the same machine.
- **Where it keeps things.** The program: `%LOCALAPPDATA%\Programs\t3med`. Electron's profile (window state, the page's localStorage, the single-instance lock): `%APPDATA%\t3med`. Everything else, patient data included: `~/.t3med`, the folder `start-t3-med.cmd` uses, so both show the same patients and chats. Only one of them can run at a time: the second is told the data folder is in use.
- **The workspace** is the `workspace` setting in `~/.t3med/userdata/t3med-desktop.json`, written with the default `D:\T3 Projects\T3 Med` at the first start (`apps/desktop/src/med/workspace.ts`). The backend is started with `--auto-bootstrap-project-from-cwd <folder>`, as `start-t3-med.cmd` does. `T3MED_WORKSPACE` in the environment wins over the file. A folder that does not exist is not opened, and the app starts without a project. A file that cannot be read as JSON (in JSON a Windows path needs doubled backslashes) falls back to the default and logs a warning.
- **The port.** The backend takes the first free port from 3900. `T3CODE_PORT` sets one.
- **Running it on other folders,** as every test must: `T3CODE_HOME` moves the data folder and `APPDATA` moves Electron's profile. These are upstream's own switches. The app still registers `t3med://` for the executable it was started from; delete `HKCU\Software\Classes\t3med` after testing an unpacked build.
- **Unsigned.** There is no code signing certificate. When the owner runs the installer, Windows SmartScreen shows "Windows protected your PC": choose **More info**, then **Run anyway**. The installer asks for no administrator rights, installs for the current user, adds `T3 Med` to the Start menu and the desktop, and starts the app. If Smart App Control is on, Windows blocks an unsigned installer outright and offers no "Run anyway".
- **Links.** The window loads from `t3med://app`. Pairing links, prompt links and the Codex sign-in handoff are still written and read as `t3code://` (`packages/shared`): they open T3 Code, not T3 Med. Signing in to Codex from inside the T3 Med window does not use such a link and works; Claude and Grok sign in through their own CLIs.
- **File count.** Upstream allows 80 files in the unpacked Windows app. A build made on Windows also carries the prepared compile cache, which only a host that can run the app generates, and has 90; `MED_WINDOWS_PAYLOAD_FILE_LIMIT` is 110.
- **Not adapted:** macOS and Linux packaging (their build configuration still names `t3code` as the link scheme, and the Linux desktop entry is upstream's), the application menu's update dialogs and a few messages that say `T3 Code`, and `apps/desktop/scripts/electron-launcher.mjs`, the development launcher.

## Patient data

Patient data lives in `t3med.sqlite`, a second SQLite file in the same state directory as upstream's database. Upstream's database is never given fork tables: its migrations are numbered, the migrator skips every id up to the highest one recorded, and a fork migration there would sooner or later take a number upstream also uses.

- Everything is under `apps/server/src/med/`: the database layer (`MedDatabase.ts`), its own migration list (`Migrations/`, recorded in the table `t3med_migrations`), the patient service (`PatientStore.ts`) and lab arithmetic (`labs.ts`). No upstream file is edited for it.
- `MedDatabase` has its own service tag, so nothing that asks for upstream's `SqlClient` can reach patient tables, and the other way round.
- The file is opened with the SQLite client directly, not through `persistence/Sqlite.ts`: that module runs upstream's migrations on whatever file it opens.
- `server.ts` provides the store once, to the whole route merge, so `/mcp` and `/api/med` share it and the file is opened once.
- **Nothing filed is ever deleted.** A lab or plan removed as a mistake keeps its row with `removed_at` set, and every list, count, baseline and chart leaves such rows out; a query that reads `labs` or `plans` must do the same. `listRemoved` is the one reader of removed rows. A corrected result keeps what it said in `lab_revisions`, one row per correction with who made it (`corrected_by`; null for a correction older than migration 004), and undoing takes the latest one back. A plan that is done or cancelled keeps in `reopens_as` whether it was a draft, so reopening never confirms it.
- **Who may change what.** `correctLab`, `setLabRemoved`, `setPlanRemoved` and `updatePlan` take an optional `threadId`. With one, the row must be filed for the thread's linked patient or from one of the thread's own notes; the agent tools always pass it. Without one, as from the doctor's routes, every row is in reach. `setLabVerified` and `setPlanVerified` take none and no tool calls them: a single row is confirmed by the doctor only.
- **What an agent changes of a plan.** Any call with a `threadId` that changes a plan's title or due date leaves the plan a draft: at once when it is open, and through `reopens_as` when it is closed, so it is a draft the next time it is open whatever closes or moves it in between. An agent marking a plan done or cancelled with no change of title or date takes effect at once and confirms nothing: the doctor said so in the chat, and reopening gives back what the plan was.
- **A correction's number and text agree.** `correctLab` refuses `valueText` that reads as a number when `value` is not sent with it, and a `value` whose `valueText` does not read as that number. `writtenNumberReadings` (`packages/contracts/src/med.ts`) reads a text the English way and the Indonesian way, so `9.800` is 9.8 or 9800 and `2,6` is 2.6; the store and the correction form both use it. Filing is not checked this way: a sheet's own text is kept beside the number the agent read.
- **An undo names what it reverses.** `undoLabCorrection` takes the `revisionId` it takes back and refuses (`RowChangedError`) when a later correction exists. Removing, verifying and changing a plan answer with the row's `updatedAt`; their undo sends it back as `ifUpdatedAt` and is refused when the row was written since. `updated_at` has millisecond resolution, so two writes in the same millisecond are not told apart. A patient's spellings are taken off and put on one by one (`removeSpellings`, `addSpellings`), so undoing a rename keeps a spelling added meanwhile.
- **A retried filing adds nothing it filed before.** A result the note has, had before a correction (`lab_revisions`), or has as a removed row is not inserted again; the same for a plan by title and due date, removed or not. A removed row comes back by restoring it, never by filing it again.
- **Verifying a note.** `verifyNote(noteId, only)` verifies exactly the lab and plan ids in `only`, of that note; the doctor's route always passes them. Without `only` it verifies every draft of the note, which is the agent's `patient_verify` and nothing else. `returnNoteRowsToDraft` is its undo.
- **A question that was dealt with.** `needs_you_handled_at` on a note says the doctor marked its question as handled. The text stays; the note stops counting on Needs you unless it also holds drafts. A filing that adds a new line to the question clears the mark, and a retry that asks the same thing does not.
- **Archiving.** `archived_from` keeps the status a patient held before archiving, and `archived: false` returns to it; a patient archived before migration 004 comes back as active.
- **Migrations are append-only.** A change to the schema is a new file in `Migrations/`: one that exists may already have run on the doctor's machine.

## Patient tools

Agents file and read patient data with the `patient_*` tools in `apps/server/src/mcp/toolkits/patient/`. Each handler calls one `PatientStore` method, so a call is one transaction: a refused lab leaves no note, plan or link behind.

- Only an agent running in a T3 Med thread may call them, reads included (`readsAsCaller`, `actsAsCaller`). Every tool is annotated `hiddenFromOutsideClients`, which upstream's `McpToolAccess` requires of a tool that acts as its calling thread: an outside MCP client that signed in over OAuth is not offered them, whatever access it was approved with, and a call from one is answered as an unknown tool. A new patient tool needs the same annotation or the server does not start.
- The tools take no thread id and no note id. The calling thread comes from the MCP credential, so a call reaches only its own thread's notes.
- A thread is linked to a patient in three places and nowhere else: `patient_find` when a URN matches exactly, `patient_create` (which needs a URN), and `patient_move_note`, the doctor's choice for the thread's Inbox note. Each says in `relinkedFrom` which patient the thread was linked to before. A name search returns `candidates` and links nothing. `PatientStore.linkThread` links on no evidence; no tool and no route calls it, and it must stay that way.
- `patient_find` always returns `linked`, the patient the thread is linked to once the call is done, beside any `match` or `candidates`. Called with no URN and no name it reads only that, so an agent can ask whom its thread is about without searching.
- `patient_file` with a patient id is refused unless the thread is linked to exactly that patient, and it never changes the link. Filing to `inbox` is always allowed. `patient_verify` verifies the thread's note for its linked patient only.
- Reading (`patient_record`) and `patient_update` take any patient's id. Filing, verifying, moving and every way back depend on the thread's link.
- The ways back are four tools. `patient_correct_lab` changes one result, which is a draft again, and clears a flag with `flag: null`; `patient_remove` takes a lab or plan out of every list, and puts it back with `restore`; `patient_update_plan` marks a plan done or cancelled, reopens it, or changes its title or due date; `patient_return_note` sends the thread's note for its linked patient back to the Inbox and leaves the thread's link alone. They name a row by the `labId` or `planId` that every lab and plan in a tool result carries. An agent's change of a plan's title or due date makes it a draft; no tool verifies a single row.
- A retried `patient_file` adds nothing: a lab the note has (same test, date, value, text and unit) or a plan it has (same title and due date) is returned as it is, a lab that was corrected since is returned as it now stands, and a row that was removed is left out of the answer. `needsYou` collects one line per question until `clearNeedsYou`. `patient_review` leaves out a question the doctor marked as handled.
- A refusal reaches the agent as the store's own message (`labs[1].testAsWritten must not be blank.`). A store failure names only the step that failed. A failure's message is written to the trace file with the span it ended, so store messages carry ids, never names. The one refusal that names a patient, a URN that is taken, is worded in the handler from the error's fields.
- A call's arguments stay out of the trace file. Effect's `Toolkit.handle` (`effect/src/ai/Toolkit.ts`, `Effect.annotateCurrentSpan({ tool, parameters })`) writes them on the current span, which for a real call is the HTTP request's. `layerPatientToolkit` runs patient calls under `withoutArgumentsOnSpan`: a copy of that span with the same ids that takes no attributes. Upstream's own tools still record theirs.
- After an upstream merge, `agentContextBudget.json` usually conflicts. Take upstream's side, run `vp test run src/provider/AgentContextBudget.test.ts` in `apps/server`, and set the file to the values the failure prints (at `v0.1.10`: upstream's 49,736 bytes plus the patient tools' 6,801). Upstream's `agent-context-budget.yml` compares a pull request with `main` and fails on growth; in this fork that growth is the patient tools.

## Patient pages

The web client reads patient data over HTTP, under `/api/med`, and sends the doctor's changes the same way. Everything is fork-owned: the contract (`packages/contracts/src/med.ts`, imported as `@t3tools/contracts/med`), the handlers (`apps/server/src/med/http.ts`), and the client (`apps/web/src/med/`, with the routes `apps/web/src/routes/_chat.{inbox,patients.index,patients.$patientId,needs-you,upcoming}.tsx`).

- **Why HTTP and not RPC.** A new RPC method is an edit to `packages/contracts/src/rpc.ts`, `ws.ts` and the client-runtime RPC layer, three files upstream changes all the time. `MedHttpApi` is its own `HttpApi`, mounted with one line in `server.ts`.
- **Signing in.** Every endpoint carries upstream's `EnvironmentAuthenticatedAuth` middleware, the one that guards `/api/projects` and `/api/orchestration`, so a cookie, a bearer token and a DPoP token are accepted and refused exactly as there, and an MCP client's session is refused. A read needs `orchestration:read`; a change needs `orchestration:operate` as well.
- **The client never links a thread.** No route writes under `/api/med/threads`, and no change a route makes touches a thread's link: a note sent back to the Inbox leaves its thread linked. `http.test.ts` lists every route, runs each one that changes something, and fails when a link is made or moved. A link written from the browser is a link made on no evidence: the draft it was written for can be reused for another patient's chat. For the same reason no route moves an Inbox note to a patient, which links its thread; that stays the agent's `patient_move_note`.
- **The doctor's changes.** Twelve routes: `PATCH` a patient, a lab or a plan; `PUT …/removed` and `PUT …/verified` on a lab or a plan; `POST /labs/:labId/undo-correction`; `POST /notes/:noteId/verify` and `…/unverify`, `PUT /notes/:noteId/question-handled` and `POST /notes/:noteId/inbox`. Each handler calls one store method without a thread id. What the store refuses comes back as `422` with the store's own sentence in `reason`, which names a field or a row's id and never a value; a missing row is `404`; an undo whose row changed since is `409` (`MedChangedSinceError`); a URN another patient holds is `409` with that patient's name in the body and not in the error's message, because the message is written to the trace.
- **Verifying confirms what was on the screen.** Needs you lists each note's draft rows (`draftLabRows`, `draftPlanRows`), and the verify route takes the ids of those rows: a draft an agent files while the page is open stays a draft. On a patient's page the same action first lists the rows in a dialog. The toast names the patient and the rows the server says it verified, and its Undo returns exactly those to draft.
- **Done at once, with Undo.** In the client a change is sent when the doctor chooses it and its toast offers Undo (`actOnMed` in `medActions.ts`). An Undo is built from the change's answer, so it names the correction or the row state it reverses, and says so when the row changed since. Only moving a note to the Inbox asks first: its results and plans become drafts again and a note merged into the Inbox note of its thread is not taken apart, so that is not undone by a click. After any change, refused or not, every patient query is read again. The controls are not rendered for a session without the operate scope.
- **Removed rows.** `GET /patients/:patientId/removed` lists what was removed for a patient. `MedRemoved` shows it folded at the foot of the patient's page (results and plans) and of the Labs and Plan surfaces (their own kind), with Restore on each row.
- **Forms send what changed.** `medChangeLogic.ts` compares a form with the row it edits, so an untouched form sends nothing. In the correction form the result as written and the number used for comparison are two fields: retyping the text sets the number when the text reads one way (`80`, `2,6`) and empties it when it reads two ways (`9.800`) or is no number, and the form will not send a pair the store would refuse.
- **No caching.** Every answer, a refusal included, carries `Cache-Control: no-store`. The header is set in a wrapper around the sign-in middleware (`layerAuth` in `http.ts`), which runs before every handler.
- **No patient text in a URL.** The request span records the full URL, query string included. So the directory is sent whole and the search runs in the browser (`filterPatients`); do not add a `?q=`. Paths carry ids only.
- **Response fields.** A handler returns what the store returns and the contract's schema drops the rest. A field a route should not give, such as `diagnoses` on a patient's home, stays out by not being in that route's schema in `med.ts`.
- **One environment.** Patient data belongs to the primary environment. `useMedEnvironmentId` (`medData.ts`) is that environment's id once the session may read there, and null until then; every patient query goes through `useMedQuery` or `useThreadPatient`, which ask nothing while it is null. So a thread of another connected environment shows no patient and is not asked about, rows that open a thread open it in the primary environment, and `New chat` uses the first project of the primary environment, by the sidebar's order, not the project last used. Without a primary environment the pages keep their loading placeholder.
- **Freshness.** The server pushes nothing for patient data. The client reads again when a patient page is entered, when the window regains focus, and when any thread starts or stops working. What an agent files in the middle of a turn shows when the turn ends.
- **A chat started from a patient's page.** `New chat` runs upstream's own new-thread handler with its `prompt` option, the one prompt links and playbooks fill a draft's composer with. The text is one line, `URN 00-12-34-56 (Ni Made Suartini)` and a line break, which the doctor sees and can change. Nothing is linked then: the agent links the thread when the message arrives, by that URN. A patient with no URN cannot be started this way, and the button says so.
- **Earlier chats.** A patient's page lists the patient's notes and, from `thread_patients`, every linked thread that filed no note for them; such a row takes its title from the client's own thread list. `Last chat` in the directory is the latest of a patient's note changes and thread links, and a dash when there is neither.
- **Rows.** A row that opens something ends with a chevron; a row that opens nothing (a note without a thread, a plan on its own patient's page) has none. Links share `MedLink`. A row's actions come after it, in a slot of fixed width, never inside the link; the line above a list is told what its rows end with (`ends` on `MedPage.Lead`) so its right column stops where theirs does.
- After an upstream merge, build the web app before type-checking: `routeTree.gen.ts` is written by the build.

## Patient surfaces in the right panel

A thread linked to a patient offers Summary, Labs, Plan and Timeline in the right panel's launcher and `+` menu, before Files and Side chat. Everything but the edits listed above is in `apps/web/src/med/`.

- **Kinds.** The surfaces are `med-summary`, `med-labs`, `med-plan` and `med-timeline` (`medSurfaces.ts`), one tab each per thread. Never name a kind `plan` or `agents`: `migratePersistedRightPanelState` drops saved surfaces of those kinds. The panel's state is in localStorage only, so the kinds are not part of any contract.
- **Whose patient.** The launcher belongs to the thread in the route. `useThreadPatientState` (`medData.ts`) tells four things apart: not known yet, the read failed, known to have none (an unlinked chat, a draft, a thread of another environment), and linked. Only the third is ever worded as "no patient is linked": a late or lost answer shows placeholders, or the failure with a retry. While not linked the four rows are disabled, and the launcher prints the one-line reason under them (`MedLauncherNote`), not only in the tooltip. Every surface starts with the patient's name and URN.
- **Row actions.** In Labs every result of the chosen test ends with a menu: verify or return to draft, correct, undo the last correction, remove. What each correction replaced is listed under the result, the latest first, with who corrected (`corrected by agent, 17 Nov`). In Plan every plan has one: verify or return to draft, mark done, cancel, reopen, change, remove. Summary and Timeline have none.
- **One read.** All four surfaces draw `GET /api/med/patients/:patientId/record`: the patient with diagnoses, every lab oldest first, every plan, every note. It is `PatientStore.getPatientRecord`, the method `patient_record` calls, with `testName` replaced for display.
- **Test names.** `testDisplayName` in `labs.ts` has one English name per Test ID. The route sends it as `testName`, so a catalogue row first named `Kolesterol LDL` reads `LDL cholesterol`; a test without a Test ID keeps the name as written. The agent tools still get the catalogue's name.
- **The client computes no lab number.** A result is shown as written (`valueText` and `unit`), in the table and beside its point on the chart. The chart plots the baseline's own value and, for every other result, the store's `valueInBaselineUnit`; a point the store converted is labelled with that number and its tooltip adds what was written. A result left off the chart is counted under it, words ("negative") apart from numbers that could not be converted. `From baseline` is the store's `changeFromBaseline`, `changePercent` and `changeUnit`.
- **Displayed numbers.** `formatLabNumber` (`medPanelLogic.ts`) is only for numbers the store worked out. It keeps four significant digits and every digit before the decimal point, so 0.004 never reads as 0, 0.008 and 0.012 stay apart, and 149.6 is not 150. A change keeps its sign; a percentage keeps two significant digits. Never pass a result as written through it.
- **The chart** (`MedLabChart.tsx`) is fork code: upstream has no chart primitive. An SVG stretched to the plot draws the lines; dots and labels are positioned in percent over it, so it follows the panel's width without being measured. A draft is a hollow dot reached by a dashed line. The height stands for at least a quarter of the largest value, so 0.9 to 1.0 does not look like 162 to 78. Results of one day sit side by side in filing order, a step apart that leaves room for the number above each dot. The accessible text says of each point whether it is a draft or verified, and the legend lists only what is drawn.
- **The chosen test** is kept per patient for the session (`selectedLabTestAtom`), so it survives switching tabs. Until one is chosen the Labs surface shows the first test, A to Z, that has two points to join. A test's name in Summary's latest results sets it and opens Labs.
- **Timeline** has two parts. `Coming up` is every open plan, overdue ones too, soonest first. `History` is what has happened, newest first: notes, lab batches by collected day, and plans done or cancelled. A lab line carries its High or Low flag and its Draft mark.
- **Narrow panel.** Below 28rem the results table folds the reference range and the status, Verified or Draft, under the result, so it fits the panel's minimum width and every result still says which it is.

## What a patient workspace hides

`T3MED` in `apps/web/src/med/t3med.ts` is the one switch. Every hidden piece of upstream UI reads it in a one-line condition, listed in the table above; nothing was deleted, and `false` gives upstream's chrome back.

- Launcher and `+` menu: Browser, Terminal, Diff, Pull request, Linked pull requests and Device are left out. `patientLauncherActions` keeps the two rows that carry the fork's `id`, `files` and `side-chat`, so upstream can reword a label without a row vanishing; `medPages.browser.test.tsx` renders upstream's own launcher and fails if either is gone. Summary takes the `S` key, so Side chat is `C`.
- Thread details menu: the editor, project scripts, branch and pull request, Git actions and changes rows. Their ids stay in client settings untouched.
- Under the composer: the environment, branch and checkout strip.
- Sidebar footer: the pull requests page entry and the update pill with its dialogs.
- Updates: the Settings updater section (desktop and hosted builds), the composer banners that offer to update a server whose version differs, and the update actions in Settings > Connections. See Updates below.

## Updates

T3 Med takes upstream's work by merging a release tag and rebuilding ([BRANDING.md](BRANDING.md)). Nothing may install an upstream build over it, so each path that could is closed:

- **`t3 update`** fails at once with `MED_UPDATE_REFUSAL` (`apps/server/src/med/updates.ts`), which says how T3 Med is updated. Nothing is looked up or written.
- **A client asking the server to update itself** (`server.updateServer` and its progress and commit calls, used by the web, desktop and mobile clients) gets the same refusal: `server.ts` provides `layerNoSelfUpdate` in place of upstream's layer.
- **Release sources.** `CLI_RELEASE_REPOSITORY` names the fork's own repository, which publishes no releases. The release index, the CLI and pinned-runtime downloads, the SSH install and the desktop app's remote-server update are all built from that constant and find nothing.
- **The web client** offers no update: the sidebar pill, the Settings updater, the composer banners and the Connections actions are behind `T3MED`.
- **The desktop app's own updater** reads `resources\app-update.yml`, which electron-builder writes only from a `publish` configuration. `medStagePackageJson` sets `publish` to null whatever `T3CODE_DESKTOP_UPDATE_REPOSITORY` or `GITHUB_REPOSITORY` say, so the file is not in the package and the updater reports that no update feed is configured. Packaging runs electron-builder with `--publish never`.

What remains, on purpose or not yet looked at:

- `T3CODE_RELEASE_BASE_URL` and a managed policy's `feedUrl` still redirect downloads. Both take a deliberate setting by whoever runs the machine, and `t3 update` and the server refuse before reading either.
- `NpmRelease` still asks the npm registry which version of upstream's `t3` package is newest. It only reports a version; nothing in T3 Med installs from npm. The hidden update button was the one place that copied an `npm install -g t3@…` command.
- `scripts/install.sh`, `scripts/npm-launcher/` and the release workflows are upstream's distribution and still name upstream. T3 Med is never installed through them.
- `MED_UPDATE_REFUSAL` set to an empty string gives upstream's update back in the CLI and the server. The release repository and the web gates are separate switches.
- The mobile app was not looked at: it can reach a T3 Med server and would be refused by it.

## Not done yet

- The browser version's favicon is upstream's until the desktop packaging has run: the fork's icons (`assets/med`) are written into the built web client by packaging, not by the web build. The mark inside the app (sidebar, splash) is upstream's T3.
- The patient surfaces show no medications or imaging.
- Nothing unlinks a thread from a patient. A thread linked to the wrong patient is corrected by giving the agent the right URN, which relinks it.
- Patient data is not pushed to the client; see Freshness above.
- The patient pages exist in the web client only. Mobile has none. In the desktop shell the sidebar, the Patients page, a chat and Settings > Providers were looked at; the right-panel surfaces were not.
- The collapsed composer of a narrow window still says `Ask anything...`: that line is in `ChatComposer.tsx`, which upstream rewrites often, and an edit there conflicted on the first merge after it was made. What a screen reader announces for the app's own messages is still `T3 Code` (`MESSAGE_AUTHOR` in `turnDetailAnnouncement.ts`), which upstream's test asserts. The CLI's help text says `T3 Code` throughout.
- Coding features are hidden where a doctor meets them every day, not everywhere: the command palette, keybindings, Settings, the pull requests page by its URL and a thread row's pull request badge still exist. `T3 Code` is still written in Settings, the command palette (`Use T3 Code in another app (MCP)`, the triage entry), the welcome page's phone and telemetry lines and the hidden update dialogs, and in `Sent by T3 Code`, which upstream's `QueuedRunsControl.browser.test.tsx` asserts.
- A filed document is recorded on its thread's note, as the note's kind and the paths of its files. It has no note of its own, and the file is not copied into the state directory.
- A note moved to the Inbox is not moved back by the doctor: an agent does that with `patient_move_note`. A note merged into another by a move is not taken apart.
- A note cannot be changed from a page: its title, summary and question are the agent's (`patient_file`). The doctor can mark a question as handled, and as waiting again from the patient's page, but not reword or delete it. A plan's type and the laboratory a result names cannot be corrected, and two records of one patient cannot be merged.
- The ways back are on the patient's page, Needs you, Labs and Plan. Upcoming, the Inbox page, Summary and Timeline still only read. A plan marked done from the patient's page leaves that page's list, which shows open plans only; it is reopened from its toast or from the Plan surface.
- A plan has no history of its titles and dates. A retried filing therefore files again a plan whose title or due date was changed since, and an undo of a plan change relies on `updatedAt` alone.
- Verifying activates a patient who was new, and undoing the verification does not make them new again.
- No eval covers the tool descriptions. `evals/mcp-tool-use` has no patient cases, so a change to a description or a schema, the four tools of the ways back included, is checked by reading it.
