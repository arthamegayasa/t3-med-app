# T3 Med fork

T3 Med is T3 Code organised around patients instead of code projects, for one doctor on a Windows laptop. This file records what the fork changes in upstream files, so an upstream merge can be checked against it. What keeps upstream's name, what carries T3 Med's, and the routine for taking an upstream release are in [BRANDING.md](BRANDING.md). Product decisions are in the workspace repo (`arthamegayasa/t3-med`, `docs/adr/`).

## Branches and remotes

- `upstream` is `pingdotgg/t3code`. Its push URL is disabled on purpose.
- `med` is T3 Med. It started from upstream tag `v0.1.8` and now sits on **`v0.1.10`**, merged on 17 November 2026 (`v0.1.9` came with it). Upstream's `package.json` still reads `0.1.9` at that tag, so a build from source runs as `0.1.9`; a release carries T3 Med's own version (Updates).
- Merge upstream from stable release tags, about once a month, by the routine in [BRANDING.md](BRANDING.md). Nightlies move too fast to follow.

## Building on Windows

- Check out to a path **without spaces**. The web build fails under a path such as `D:\T3 Projects\…` (`UNLOADABLE_DEPENDENCY`, os error 123), because a worker entry is resolved from a URL-encoded path.
- Install `vp` (`irm https://vite.plus/ps1 | iex`), then from the repository root: `vp i`, `vp run --filter t3 build`.
- Run the built server: `node apps/server/dist/bin.mjs serve --port 3899` with the Node that `vp` provides (Node 26). It serves the web UI on that port.
- The background service does not exist on Windows; the server runs in the foreground.
- The web client's browser tests (`*.browser.test.tsx`) need Playwright's Chromium shell once: `node apps/web/node_modules/playwright/cli.js install --only-shell chromium`. Then, in `apps/web`, `vp test run --project browser <files>`.
- `start-t3-med.cmd` in the repository root starts the built server on port 3899 with the patient workspace (`D:\T3 Projects\T3 Med`) as its project and opens the browser. Closing its window stops T3 Med.
- `build-t3-med-installer.cmd` builds the desktop app's installer; see The desktop app. A release is built by the same script on GitHub; see Updates.

## The desktop app

T3 Med has a Windows desktop app: upstream's Electron app (`apps/desktop`) built by upstream's packaging script, with the fork's identity. `start-t3-med.cmd` still works and is the fallback.

- **Build the installer:** `build-t3-med-installer.cmd` in the repository root. It builds upstream's resource monitor with Cargo, then runs `node scripts/build-desktop-artifact.ts --platform win --target nsis --arch x64`. The installer is `release\T3-Med-<version>-x64.exe` (about 210 MB; `release/` is ignored by git). It takes about seven minutes. Without `--build-version` the build carries upstream's manifest version (`0.1.9`), which is below every release, so an app installed from it downloads the newest release at once; a release is built by the workflow in Updates. It rebuilds `apps/server/dist`, the tree `start-t3-med.cmd` serves, so close the browser version before building. It reads the `T3CODE_DESKTOP_*` variables and any `.env` of the shell it runs in; run it from a plain shell and pass it no arguments.
- **What the build needs:** `vp`, Python 3, Rust (`rustup`, installed per user, with the `x86_64-pc-windows-msvc` target) and the Visual Studio C++ build tools with a Windows SDK. Upstream's own preflight also demands the Spectre-mitigated MSVC libraries, which need an administrator to install and which nothing in the build uses; the script avoids that check with upstream's `T3CODE_DESKTOP_REUSE_RESOURCE_MONITOR`, the switch upstream's release workflow sets.
- **Identity** is in `scripts/lib/med-identity.ts`, read by the app through `apps/desktop/src/med/identity.ts` and by packaging through `scripts/med/desktop-package.ts`: product name `T3 Med`, app id `com.arthamegayasa.t3med`, package name `t3med`, scheme `t3med`. Nothing may equal T3 Code's value, because T3 Code is installed on the same machine.
- **Where it keeps things.** The program: `%LOCALAPPDATA%\Programs\t3med`. Electron's profile (window state, the page's localStorage, the single-instance lock): `%APPDATA%\t3med`. Everything else, patient data included: `~/.t3med`, the folder `start-t3-med.cmd` uses, so both show the same patients and chats. Only one of them can run at a time: the second is told the data folder is in use.
- **The workspace** is the `workspace` setting in `~/.t3med/userdata/t3med-desktop.json`, written with the default `D:\T3 Projects\T3 Med` at the first start (`apps/desktop/src/med/workspace.ts`). The backend is started with `--auto-bootstrap-project-from-cwd <folder>`, as `start-t3-med.cmd` does. `T3MED_WORKSPACE` in the environment wins over the file. A folder that does not exist is not opened, and the app starts without a project. A file that cannot be read as JSON (in JSON a Windows path needs doubled backslashes) falls back to the default and logs a warning.
- **The port.** The backend takes the first free port from 3900. `T3CODE_PORT` sets one.
- **Running it on other folders,** as every test must: `T3CODE_HOME` moves the data folder, `APPDATA` moves Electron's profile, and `LOCALAPPDATA` moves the folder an update is downloaded to (`t3med-updater`). These are upstream's own switches, or Windows'. Set `T3MED_WORKSPACE` to a temporary folder too, or the app opens the patient workspace. The app still registers `t3med://` for the executable it was started from; delete `HKCU\Software\Classes\t3med` after testing an unpacked build.
- **Unsigned.** There is no code signing certificate. When the owner runs the installer, Windows SmartScreen shows "Windows protected your PC": choose **More info**, then **Run anyway**. The installer asks for no administrator rights, installs for the current user, adds `T3 Med` to the Start menu and the desktop, and starts the app. If Smart App Control is on, Windows blocks an unsigned installer outright and offers no "Run anyway". What an unsigned build means for an update is in Updates.
- **Links.** The window loads from `t3med://app`. Pairing links, prompt links and the Codex sign-in handoff are still written and read as `t3code://` (`packages/shared`): they open T3 Code, not T3 Med. Signing in to Codex from inside the T3 Med window does not use such a link and works; Claude and Grok sign in through their own CLIs.
- **File count.** Upstream allows 80 files in the unpacked Windows app. A build made on Windows also carries the prepared compile cache, which only a host that can run the app generates, and has 90; `MED_WINDOWS_PAYLOAD_FILE_LIMIT` is 110.
- **Not adapted:** macOS and Linux packaging (their build configuration still names `t3code` as the link scheme, the Linux desktop entry is upstream's, and no release is built for them), a few messages that say `T3 Code` (a managed policy's sentence where upstream's tests pin it; see Updates), and `apps/desktop/scripts/electron-launcher.mjs`, the development launcher.

## Patient data

Patient data lives in `t3med.sqlite`, a second SQLite file in the same state directory as upstream's database. Upstream's database is never given fork tables: its migrations are numbered, the migrator skips every id up to the highest one recorded, and a fork migration there would sooner or later take a number upstream also uses.

- Everything is under `apps/server/src/med/`: the database layer (`MedDatabase.ts`), its own migration list (`Migrations/`, recorded in the table `t3med_migrations`), the patient service (`PatientStore.ts`) and lab arithmetic (`labs.ts`). No upstream file is edited for it.
- `MedDatabase` has its own service tag, so nothing that asks for upstream's `SqlClient` can reach patient tables, and the other way round.
- The file is opened with the SQLite client directly, not through `persistence/Sqlite.ts`: that module runs upstream's migrations on whatever file it opens.
- `server.ts` provides the store once, to the whole route merge, so `/mcp` and `/api/med` share it and the file is opened once.
- **Nothing filed is ever deleted.** A lab or plan removed as a mistake keeps its row with `removed_at` set, and every list, count, baseline and chart leaves such rows out; a query that reads `labs` or `plans` must do the same. `listRemoved` is the one reader of removed rows. A corrected result keeps what it said in `lab_revisions`, one row per correction with who made it (`corrected_by`; null for a correction older than migration 004), and undoing takes the latest one back. A plan that is done or cancelled keeps in `reopens_as` whether it was a draft, so reopening never confirms it.
- **Who may change what.** `correctLab`, `setLabRemoved`, `setPlanRemoved` and `updatePlan` take an optional `threadId`. With one, the row must be filed for the thread's linked patient or from one of the thread's own notes; the agent tools always pass it. Without one, as from the doctor's routes, every row is in reach. `setLabVerified` and `setPlanVerified` take none and no tool calls them: a single row is confirmed by the doctor only.
- **What an agent changes of a plan.** Any call with a `threadId` that changes a plan's title or due date leaves the plan a draft: at once when it is open, and through `reopens_as` when it is closed, so it is a draft the next time it is open whatever closes or moves it in between. An agent marking a plan done or cancelled with no change of title or date takes effect at once and confirms nothing: the doctor said so in the chat, and reopening gives back what the plan was.
- **A correction's number and text agree.** `correctLab` refuses `valueText` that reads as a number when `value` is not sent with it, and a `value` whose `valueText` does not read as that number. `writtenNumberReadings` (`packages/contracts/src/med.ts`) reads a text the English way and the Indonesian way, so `9.800` is 9.8 or 9800 and `2,6` is 2.6; the store and the correction form both use it. Filing is not checked this way: a sheet's own text is kept beside the number the agent read.
- **An undo names what it reverses.** `undoLabCorrection` takes the `revisionId` it takes back and refuses (`RowChangedError`) when a later correction exists. Removing, verifying and changing a plan answer with the row's `updatedAt`; their undo sends it back as `ifUpdatedAt` and is refused when the row was written since. `updated_at` has millisecond resolution, so two writes in the same millisecond are not told apart. A patient's spellings are taken off and put on one by one (`removeSpellings`, `addSpellings`), so undoing a rename keeps a spelling added meanwhile.
- **A retried filing adds nothing it filed before.** A result the note has, had before a correction (`lab_revisions`), or has as a removed row is not inserted again; the same for a plan by title and due date, removed or not. A removed row comes back by restoring it, never by filing it again.
- **Verifying a note.** `verifyNote(noteId, only)` verifies exactly the lab and plan ids in `only`, of that note; the doctor's route always passes them. Without `only` it verifies every draft of the note, which is the agent's `patient_verify` and nothing else. `returnNoteRowsToDraft` is its undo.
- **A question that was dealt with.** `needs_you_handled_at` on a note says the doctor marked its question as handled. The text stays; the note stops counting on Needs you unless it also holds drafts. A filing that adds a new line to the question clears the mark, and a retry that asks the same thing does not.
- **Archiving.** `archived_from` keeps the status a patient held before archiving, and `archived: false` returns to it; a patient archived before migration 004 comes back as active.
- **Migrations are append-only.** A change to the schema is a new file in `Migrations/`: one that exists may already have run on the doctor's machine.

## Patient tools

Agents file and read patient data with the `patient_*` tools in `apps/server/src/mcp/toolkits/patient/`. Each handler calls one `PatientStore` method, so a call is one transaction: a refused lab leaves no note, plan or link behind.

- Only an agent running in a T3 Med thread may call them, reads included (`readsAsCaller`, `actsAsCaller`). Every tool is annotated `hiddenFromOutsideClients`, which upstream's `McpToolAccess` requires of a tool that acts as its calling thread: an outside MCP client that signed in over OAuth is not offered them, whatever access it was approved with, and a call from one is answered as an unknown tool. A new patient tool needs the same annotation or the server does not start.
- The tools take no thread id and no note id. The calling thread comes from the MCP credential, so a call reaches only its own thread's notes.
- A thread is linked to a patient in three places and nowhere else: `patient_find` when a URN matches exactly, `patient_create` (which needs a URN), and `patient_move_note`, the doctor's choice for the thread's Inbox note. Each says in `relinkedFrom` which patient the thread was linked to before. A name search returns `candidates` and links nothing. `PatientStore.linkThread` links on no evidence; no tool and no route calls it, and it must stay that way.
- `patient_find` always returns `linked`, the patient the thread is linked to once the call is done, beside any `match` or `candidates`. Called with no URN and no name it reads only that, so an agent can ask whom its thread is about without searching.
- `patient_file` with a patient id is refused unless the thread is linked to exactly that patient, and it never changes the link. Filing to `inbox` is always allowed. `patient_verify` verifies the thread's note for its linked patient only.
- Reading (`patient_record`) and `patient_update` take any patient's id. Filing, verifying, moving and every way back depend on the thread's link.
- The ways back are four tools. `patient_correct_lab` changes one result, which is a draft again, and clears a flag with `flag: null`; `patient_remove` takes a lab or plan out of every list, and puts it back with `restore`; `patient_update_plan` marks a plan done or cancelled, reopens it, or changes its title or due date; `patient_return_note` sends the thread's note for its linked patient back to the Inbox and leaves the thread's link alone. They name a row by the `labId` or `planId` that every lab and plan in a tool result carries. An agent's change of a plan's title or due date makes it a draft; no tool verifies a single row.
- A retried `patient_file` adds nothing: a lab the note has (same test, date, value, text and unit) or a plan it has (same title and due date) is returned as it is, a lab that was corrected since is returned as it now stands, and a row that was removed is left out of the answer. `needsYou` collects one line per question until `clearNeedsYou`. `patient_review` leaves out a question the doctor marked as handled.
- A refusal reaches the agent as the store's own message (`labs[1].testAsWritten must not be blank.`). A store failure names only the step that failed. A failure's message is written to the trace file with the span it ended, so store messages carry ids, never names. The one refusal that names a patient, a URN that is taken, is worded in the handler from the error's fields.
- A call's arguments stay out of the trace file. Effect's `Toolkit.handle` (`effect/src/ai/Toolkit.ts`, `Effect.annotateCurrentSpan({ tool, parameters })`) writes them on the current span, which for a real call is the HTTP request's. `layerPatientToolkit` runs patient calls under `withoutArgumentsOnSpan`: a copy of that span with the same ids that takes no attributes. Upstream's own tools still record theirs.
- After an upstream merge, `agentContextBudget.json` usually conflicts. Take upstream's side, run `vp test run src/provider/AgentContextBudget.test.ts` in `apps/server`, and set the file to the values the failure prints (at `v0.1.10`: upstream's 49,736 bytes plus the patient tools' 6,801). Upstream's `agent-context-budget.yml` compares a pull request with `main` and fails on growth; in this fork that growth is the patient tools.

## Patient pages

The web client reads patient data over HTTP, under `/api/med`, and sends the doctor's changes the same way. Everything is fork-owned: the contract (`packages/contracts/src/med.ts`, imported as `@t3tools/contracts/med`), the handlers (`apps/server/src/med/http.ts`), and the client (`apps/web/src/med/`, with the routes `apps/web/src/routes/_chat.{inbox,patients.index,patients.$patientId,needs-you,upcoming}.tsx`).

- **Why HTTP and not RPC.** A new RPC method is an edit to `packages/contracts/src/rpc.ts`, `ws.ts` and the client-runtime RPC layer, three files upstream changes all the time. `MedHttpApi` is its own `HttpApi`, mounted with one line in `server.ts`.
- **Signing in.** Every endpoint carries upstream's `EnvironmentAuthenticatedAuth` middleware, the one that guards `/api/projects` and `/api/orchestration`, so a cookie, a bearer token and a DPoP token are accepted and refused exactly as there, and an MCP client's session is refused. A read needs `orchestration:read`; a change needs `orchestration:operate` as well.
- **The client never links a thread.** No route writes under `/api/med/threads`, and no change a route makes touches a thread's link: a note sent back to the Inbox leaves its thread linked. `http.test.ts` lists every route, runs each one that changes something, and fails when a link is made or moved. A link written from the browser is a link made on no evidence: the draft it was written for can be reused for another patient's chat. For the same reason no route moves an Inbox note to a patient, which links its thread; that stays the agent's `patient_move_note`.
- **The doctor's changes.** Twelve routes: `PATCH` a patient, a lab or a plan; `PUT …/removed` and `PUT …/verified` on a lab or a plan; `POST /labs/:labId/undo-correction`; `POST /notes/:noteId/verify` and `…/unverify`, `PUT /notes/:noteId/question-handled` and `POST /notes/:noteId/inbox`. Each handler calls one store method without a thread id. What the store refuses comes back as `422` with the store's own sentence in `reason`, which names a field or a row's id and never a value; a missing row is `404`; an undo whose row changed since is `409` (`MedChangedSinceError`); a URN another patient holds is `409` with that patient's name in the body and not in the error's message, because the message is written to the trace.
- **Verifying confirms what was on the screen.** Needs you lists each note's draft rows (`draftLabRows`, `draftPlanRows`), and the verify route takes the ids of those rows: a draft an agent files while the page is open stays a draft. On a patient's page the same action first lists the rows in a dialog. The toast names the patient and the rows the server says it verified, and its Undo returns exactly those to draft.
- **Done at once, with Undo.** In the client a change is sent when the doctor chooses it and its toast offers Undo (`actOnMed` in `medActions.ts`). An Undo is built from the change's answer, so it names the correction or the row state it reverses, and says so when the row changed since. Only moving a note to the Inbox asks first: its results and plans become drafts again and a note merged into the Inbox note of its thread is not taken apart, so that is not undone by a click. After any change, refused or not, every patient query is read again. The controls are not rendered for a session without the operate scope.
- **Removed rows.** `GET /patients/:patientId/removed` lists what was removed for a patient. `MedRemoved` shows it folded at the foot of the patient's page (results and plans) and of the Labs and Plan surfaces (their own kind), with Restore on each row.
- **Forms send what changed.** `medChangeLogic.ts` compares a form with the row it edits, so an untouched form sends nothing. In the correction form the result as written and the number used for comparison are two fields: retyping the text sets the number when the text reads one way (`80`, `2,6`) and empties it when it reads two ways (`9.800`) or is no number, and the form will not send a pair the store would refuse.
- **No caching.** Every answer, a refusal included, carries `Cache-Control: no-store`. The header is set in a wrapper around the sign-in middleware (`layerAuth` in `http.ts`), which runs before every handler.
- **No patient text in a URL.** The request span records the full URL, query string included. So the directory is sent whole and the search runs in the browser (`filterPatients`); do not add a `?q=`. Paths carry ids only.
- **Response fields.** A handler returns what the store returns and the contract's schema drops the rest. A field a route should not give, such as `diagnoses` on a patient's home, stays out by not being in that route's schema in `med.ts`.
- **One environment.** Patient data belongs to the primary environment. `useMedEnvironmentId` (`medData.ts`) is that environment's id once the session may read there, and null until then; every patient query goes through `useMedQuery` or `useThreadPatient`, which ask nothing while it is null. So a thread of another connected environment shows no patient and is not asked about, rows that open a thread open it in the primary environment, and `New chat` uses the first project of the primary environment, by the sidebar's order, not the project last used. Without a primary environment the pages keep their loading placeholder.
- **Freshness.** The server pushes nothing for patient data. The client reads again when a patient page is entered, when the window regains focus, and when any thread starts or stops working. What an agent files in the middle of a turn shows when the turn ends.
- **A chat started from a patient's page.** `New chat` runs upstream's own new-thread handler with its `prompt` option, the one prompt links and playbooks fill a draft's composer with. The text is one line, `URN 00-12-34-56 (Ni Made Suartini)` and a line break, which the doctor sees and can change. Nothing is linked then: the agent links the thread when the message arrives, by that URN. A patient with no URN cannot be started this way, and the button says so.
- **Every thread's patient.** `GET /api/med/thread-patients` answers for the whole thread list at once; see The patient on a sidebar row.
- **Earlier chats.** A patient's page lists the patient's notes and, from `thread_patients`, every linked thread that filed no note for them; such a row takes its title from the client's own thread list. `Last chat` in the directory is the latest of a patient's note changes and thread links, and a dash when there is neither.
- **Rows.** A row that opens something ends with a chevron; a row that opens nothing (a note without a thread, a plan on its own patient's page) has none. Links share `MedLink`. A row's actions come after it, in a slot of fixed width, never inside the link; the line above a list is told what its rows end with (`ends` on `MedPage.Lead`) so its right column stops where theirs does.
- After an upstream merge, build the web app before type-checking: `routeTree.gen.ts` is written by the build.

## Patient surfaces in the right panel

A thread linked to a patient offers Summary, Labs, Plan and Timeline in the right panel's launcher and `+` menu, before Side chat. Everything but the edits listed above is in `apps/web/src/med/`.

- **Kinds.** The surfaces are `med-summary`, `med-labs`, `med-plan` and `med-timeline` (`medSurfaces.ts`), one tab each per thread. Never name a kind `plan` or `agents`: `migratePersistedRightPanelState` drops saved surfaces of those kinds. The panel's state is in localStorage only, so the kinds are not part of any contract.
- **Whose patient.** The launcher belongs to the thread in the route. `useThreadPatientState` (`medData.ts`) tells four things apart: not known yet, the read failed, known to have none (an unlinked chat, a draft, a thread of another environment), and linked. Only the third is ever worded as "no patient is linked": a late or lost answer shows placeholders, or the failure with a retry. While not linked the four rows are disabled, and the launcher prints the one-line reason under them (`MedLauncherNote`), not only in the tooltip. Every surface starts with the patient's name and URN.
- **Row actions.** In Labs every result of the chosen test ends with a menu: verify or return to draft, correct, undo the last correction, remove. What each correction replaced is listed under the result, the latest first, with who corrected (`corrected by agent, 17 Nov`). In Plan every plan has one: verify or return to draft, mark done, cancel, reopen, change, remove. Summary and Timeline have none.
- **One read.** All four surfaces draw `GET /api/med/patients/:patientId/record`: the patient with diagnoses, every lab oldest first, every plan, every note. It is `PatientStore.getPatientRecord`, the method `patient_record` calls, with `testName` replaced for display.
- **Test names.** `testDisplayName` in `labs.ts` has one English name per Test ID. The route sends it as `testName`, so a catalogue row first named `Kolesterol LDL` reads `LDL cholesterol`; a test without a Test ID keeps the name as written. The agent tools still get the catalogue's name.
- **The client computes no lab number.** A result is shown as written (`valueText` and `unit`), in the table and beside its point on the chart. The chart plots the baseline's own value and, for every other result, the store's `valueInBaselineUnit`; a point the store converted is labelled with that number and its tooltip adds what was written. A result left off the chart is counted under it, words ("negative") apart from numbers that could not be converted. `From baseline` is the store's `changeFromBaseline`, `changePercent` and `changeUnit`.
- **Displayed numbers.** `formatLabNumber` (`medPanelLogic.ts`) is only for numbers the store worked out. It keeps four significant digits and every digit before the decimal point, so 0.004 never reads as 0, 0.008 and 0.012 stay apart, and 149.6 is not 150. A change keeps its sign; a percentage keeps two significant digits. Never pass a result as written through it.
- **The chart** (`MedLabChart.tsx`) is fork code: upstream has no chart primitive. An SVG stretched to the plot draws the lines; dots and labels are positioned in percent over it, so it follows the panel's width without being measured. A draft is a hollow dot reached by a dashed line. The height stands for at least a quarter of the largest value, so 0.9 to 1.0 does not look like 162 to 78. Results of one day sit side by side in filing order, a step apart that leaves room for the number above each dot. The accessible text says of each point whether it is a draft or verified, and the legend lists only what is drawn.
- **The chosen test** is kept per patient for the session (`selectedLabTestAtom`), so it survives switching tabs. Until one is chosen the Labs surface shows the first test, A to Z, that has two points to join. A test's name in Summary's latest results sets it and opens Labs.
- **Timeline** has two parts. `Coming up` is every open plan, overdue ones too, soonest first. `History` is what has happened, newest first: notes, lab batches by collected day, and plans done or cancelled. A lab line carries its High or Low flag and its Draft mark.
- **Narrow panel.** Below 28rem the results table folds the reference range and the status, Verified or Draft, under the result, so it fits the panel's minimum width and every result still says which it is.

### Permissions

The doctor decided: an agent may use the patient tools freely, and must ask before it runs a command or changes a file.

- **A new thread starts Supervised** (`approval-required`), where upstream's starts in Full access. Upstream's constants are unchanged. On the server `medPolicy` (`apps/server/src/med/settingsDefaults.ts`) lays the default under upstream's managed-settings policy in the live policy layer, so a settings file that does not say reads Supervised, the doctor's choice in Settings > Threads > Permissions is written to the file and wins, and a managed policy's own default is kept. In the client `medRuntimeMode` gives the same mode to a draft made without one and to the Reset button. A thread keeps the mode it has; the mode is changed per thread in the model picker's footer.
- **The patient tools never wait for approval in that mode.** `PATIENT_TOOL_NAMES` and `isPatientToolCall` (`packages/contracts/src/med.ts`) name exactly the thirteen tools of the app's own MCP server; `toolApproval.test.ts` holds the list to the toolkit's. Nothing wider is allowed: a shell command, a file write, a web fetch, another MCP server's tool and upstream's own non-patient tools ask as before, except where the next lines say upstream already lets them through.
  - **Claude.** Upstream pre-approves the whole `t3-code` server (`mcp__t3-code__*` in `allowedTools`) in every mode that is not read-only, so the patient tools already ran unasked and nothing was changed. Upstream's other tools on that server run unasked too; that is upstream's choice, not the fork's. Proven by test at upstream's own seam (`claudeRuntimeQueryPolicyForRuntimePolicy`, `claudeMcpQueryOverrides`).
  - **Codex.** In that mode Codex runs with `untrusted` approvals and raises a tool-call approval as an MCP elicitation, which upstream shows the doctor. `isPatientToolApproval` (`apps/server/src/med/toolApproval.ts`) answers it when the elicitation is Codex's own approval of a tool call (`codex_approval_kind: "mcp_tool_call"`), the server is `t3-code` and `tool_name` is a patient tool. The predicate is proven by test; that Codex sends those two keys was read from the strings of `codex-cli 0.169.0`, and was not run. A Codex that names the tool differently keeps asking.
  - **Grok and the other ACP agents.** `patientToolDisposition` (`packages/provider-acp/src/server/med/patientToolApproval.ts`) lifts "ask" to "allow" in Supervised only, for a call the provider itself marked as an MCP call (`is_mcp_tool_call`) with the server and tool as fields. It does not read titles or `acp-mcp-call` command lines, which a shell command can spell. Proven by test with the updates Grok 1.0.77 sends for a `use_tool` call. Agents whose calls are not marked that way (Kiro, fx, Cursor, OpenCode, Pi, Muse, Antigravity) keep asking; they were not looked at further.

## Updates

The desktop app updates itself from T3 Med's own GitHub Releases: it looks for a new version in the background, downloads it, and asks one thing, when to restart. Nothing may install an upstream build over T3 Med, so the fork's releases are the only source and every other path stays closed. T3 Med still takes upstream's work by merging a release tag and rebuilding ([BRANDING.md](BRANDING.md)).

### The feed

- **One name, in one file.** `packages/shared/src/medRelease.ts` names the repository (`arthamegayasa/t3-med-app`), the tag prefix and the version scheme. The update feed, `CLI_RELEASE_REPOSITORY`, the release links in the web client and in the "could not start" window, and the release workflow's scripts all import it. No source names `pingdotgg/t3code` as a place to fetch a build from.
- **What the installed app reads.** electron-updater reads `resources\app-update.yml`, unless the app hands it another feed at start; the two cases in which upstream's code does are below. electron-builder writes that file from the staged package's `publish`, and `medStagePackageJson` (`scripts/med/desktop-package.ts`) sets `publish` to the fork's feed whatever upstream's script resolved from `T3CODE_DESKTOP_UPDATE_REPOSITORY`, `GITHUB_REPOSITORY` or a mock-update flag. The file holds `provider: github`, `owner`, `repo`, `releaseType: release` and the cache folder's name. There is no fallback feed, mirror, channel or CDN.
- **The mock feed is ignored.** `T3CODE_DESKTOP_MOCK_UPDATES` makes upstream's app read a plain-HTTP feed on localhost, and any process of the user can set it. A package that carries its own `app-update.yml`, as every T3 Med package does, never takes it (`medTakesMockFeed`, `apps/desktop/src/med/updates.ts`).
- **A managed policy's `feedUrl` stays.** A policy file can turn updates off or name an HTTPS mirror. It is `C:\Program Files\T3Code\policy.json`, the same file T3 Code reads, and writing it takes an administrator. Nothing on the doctor's machine creates it. A mirror that serves upstream's releases offers T3 Med nothing: every T3 Med version is above every upstream version, and the updater never goes down. Its messages say `T3 Med` (`medUpdatePolicy`), except the sentence `<organization> manages T3 Code updates.` where it marks a locked setting or fails a check from the web client: upstream's tests pin it in `packages/contracts`.
- **One track.** T3 Med publishes stable releases only, and Settings has no Stable or Nightly picker. A track saved in `desktop-settings.json` by hand or by an older build is read as stable (`medDesktopSettings`); the file is not rewritten. Without that, a saved `nightly` would look for a pre-release feed that does not exist and fail every check.
- **What a check does.** The app asks `github.com/arthamegayasa/t3-med-app/releases/latest` for the newest release that is neither a draft nor a pre-release, reads that release's `latest.yml`, and takes its version when semver calls it newer than the running one. A download is verified against the SHA-512 in `latest.yml`.
- **Checked on the package, not only on source.** Before a release is published, `scripts/med/verify-update-package.ts` reads four things and refuses the release on any of them: `app-update.yml` taken out of the built installer (any owner, repository, provider, address, channel or publisher name but the fork's); `latest.yml` against the installer's own name, size and SHA-512; the manifest inside the packaged `app.asar` (a version other than the one being released); and the configuration electron-builder made the installer from, the staged `package.json`, which the build keeps for this (`deleteAppDataOnUninstall` anything but `false`, any `publish` but the fork's alone, another `appId`). electron-builder leaves that configuration out of the package, so it is read from the stage folder of the same build.

### What the doctor sees

From "a new version exists" to "running it":

1. **Nothing, at first.** The app checks 15 seconds after it starts and every 4 hours. When it finds a release it downloads it by itself (about 210 MB); the small update button at the foot of the sidebar shows a progress ring, and its tooltip says `Downloading update 2026.11.3 (41%)`. No click is needed and nothing is asked.
2. **One notice.** When the download is done a toast says `Update 2026.11.3 is ready`, once for that version, also across restarts of the app. The mark that it was said is kept in the page's storage, which Chromium writes to disk within about a minute: an app that is killed sooner says it once more at its next start.
3. **One button.** A button at the foot of the sidebar says `Restart to update to 2026.11.3` and stays until the app has restarted. The small update button beside it shows the release's `What's changed` on hover, and Settings > About says `Update 2026.11.3 is downloaded. Restart T3 Med to install it.` beside `Restart to update`.
4. **One question.** The click asks `Restart T3 Med to update to 2026.11.3?` and warns that a chat that is still running will be interrupted. On OK the app closes, the installer runs silently for a few seconds, and T3 Med opens again on the new version.
5. **Or later.** A doctor who never clicks gets the update anyway: closing T3 Med with a downloaded update installs it, silently, and the next start is the new version. The app is not started again by that install. Opening T3 Med again within the half minute the installer needs can find it closing again or failing to open; open it once more.
6. **After a restart of the app without installing** (the app was stopped, not closed, or the install did not run) the downloaded file is still there: the next check offers `Restart to update` again within seconds, with no new download and no second notice.

- **A download that fails** leaves the update offered: the small button's tooltip says `Download failed for 2026.11.3. Click to retry.`, and the app tries again by itself after an hour.
- **By hand.** Settings > About > `Check for Updates`, on the Version row, which reads `Version 2026.11.2  built on T3 Code 0.1.10`. The small update button in the sidebar does the same when nothing is offered. Help > Check for Updates... exists in the application menu, but the Windows window has no menu bar: it is built with a hidden title bar, and pressing Alt in the running app showed none. A build made from source shows `from source` on the Version row instead of a number.
- **Only the app.** The update button never adds a provider's CLI or another machine's server to the update: under `T3MED` `useUpdateEverything.ts` collects neither, so the "update everything" dialog never opens.
- **When T3 Med cannot start**, the "could not start" window offers the update too, and its links lead to the fork's release page.
- **How it is built.** `apps/desktop/src/med/updates.ts` wraps upstream's update service where `main.ts` puts the app together: it starts the download when upstream's state says an update is available, and turns on electron-updater's install on quit. `MED_DOWNLOADS_UPDATES` and `MED_INSTALLS_ON_QUIT` set to `false` give upstream's two clicks back. The words are in `apps/web/src/med/medUpdateWording.ts`, the button in `MedUpdateReady.tsx`, the notice in `medUpdateAnnounce.ts`.

### Versions

A T3 Med version is `<year>.<month>.<release>`: `2026.11.2` is the second release of November 2026. The tag is `med-v2026.11.2`.

- **Why not upstream's number.** Upstream's `package.json` says `0.1.9` at the tag `v0.1.10`, moves at every merge, and editing it would conflict at every merge. No `package.json` is edited: the workflow passes `--build-version`, upstream's script writes that version into the manifests for the length of the build and puts them back.
- **Why no pre-release part.** `0.1.10-med.2` would be semver-older than `0.1.10`, and electron-builder and electron-updater read a pre-release word as an update channel (`med.yml` instead of `latest.yml`). A version is three plain numbers, so the only comparison is the numeric one. `medRelease.test.ts` checks every pair of a list of releases against upstream's own `compareSemverVersions`.
- **Always above.** Year first, so a release is newer than every earlier one and than any version upstream's manifest can hold (`0.1.9` today). An app installed from a local build made since the feed was added runs as upstream's version and is offered the newest release at once. The `0.1.9` installer built before that carries no `app-update.yml`, so an app installed from it never checks: install a release over it by hand, once.
- **Refused by the workflow:** a version that is not above every published release and every `med-v*` tag (but the run's own), a tag of another shape, and a version with a pre-release or build part (`scripts/med/release-version.ts`). Draft releases are not counted: GitHub lists a draft only to a token that can push, and the build job's token cannot. This was read in GitHub's documentation, not tried.
- **The upstream version** shown beside it is `MED_UPSTREAM_VERSION` in `medRelease.ts`, changed in the commit that records an upstream merge. `scripts/med/upstream-version.test.ts` fails when it is not the newest upstream release tag merged into the checkout. It is not read from upstream's manifest, which lags the tag, and it passes without looking in a clone that has no upstream tags, as on the release runner.
- **`v<version>` tags are upstream's** and arrive with `git fetch upstream --tags`; the fork's tags start with `med-v`. Upstream's release index (`t3 update`, the remote-server update) looks for `v<version>` and `t3-*` archives and finds neither in the fork's releases.

### Releasing

`.github/workflows/med-release.yml` is the fork's one workflow. It runs for a pushed `med-v*` tag and for a manual run, on a GitHub-hosted Windows runner, with no secret but the built-in token: the build job has `contents: read`, the publish job `contents: write`. It runs `build-t3-med-installer.cmd --build-version <version> --keep-stage`, the script the owner runs by hand, checks the package as described above, writes the release notes, and publishes a GitHub Release with three files: `T3-Med-<version>-x64.exe`, its `.blockmap`, and `latest.yml`. Nothing goes to npm, a store, a relay or anywhere else.

**Only what is on `med` is released.** The workflow refuses a tag whose commit is not `origin/med`'s head or one of its ancestors, and a manual run started on any ref but `med` (`scripts/med/release-commit.ts`). So the sequence is: merge to `med`, push `med`, then tag.

```sh
# 1. What is being released is on med, and med is pushed.
git checkout med && git merge --ff-only <branch> && git push origin med

# 2. The next version: one above the newest of these.
git ls-remote --tags origin 'med-v*'

# 3. Tag med's head and push the tag. The push starts the workflow.
git tag med-v2026.11.3 med && git push origin med-v2026.11.3

# 4. Watch it, then read what was published.
gh run watch -R arthamegayasa/t3-med-app "$(gh run list -R arthamegayasa/t3-med-app --workflow med-release.yml --limit 1 --json databaseId --jq '.[0].databaseId')" --exit-status
gh release view med-v2026.11.3 -R arthamegayasa/t3-med-app --json tagName,url,isDraft,assets --jq '{tagName, url, isDraft, assets: [.assets[].name]}'
```

A manual run does steps 2 and 3 by itself, taking the next version and creating the tag when it publishes: `gh workflow run med-release.yml -R arthamegayasa/t3-med-app --ref med` (`-f version=2026.12.1` names one). Use `-R arthamegayasa/t3-med-app` on every `gh` command: the checkout has an `upstream` remote and `gh` has picked it before.

- **Watch for:** the run ending green (about 8 minutes before the history fetch and the notes were added, which take seconds), and the last command listing the three files under the new tag with `isDraft` false. A release is published only after its files are uploaded, so an installed app never finds one without `latest.yml`.
- **A `med-v*` tag cannot be deleted or moved** once pushed: the repository has a tag ruleset. A tag is spent when it is pushed, whether or not its build succeeds.
- **If the build job fails,** nothing was published and no installed app sees anything. What is left: the tag, if one was pushed, and nothing else. When trying again can cure it (a download that timed out), run the same run again: `gh run rerun <run id> --failed -R arthamegayasa/t3-med-app`. When it needs a change to the code, the tag's commit cannot change: merge the fix to `med` and tag the next number. A manual run that failed left no tag, and running it again takes the same number.
- **If the publish job fails,** the installer exists as the run's artifact for 7 days, and a draft release may be left. A draft is invisible to installed apps. Delete it, then run the failed job again, which publishes the same files: `gh release delete med-v2026.11.3 -R arthamegayasa/t3-med-app --yes`, then `gh run rerun <run id> --failed -R arthamegayasa/t3-med-app`.
- **What the doctor reads about a release** is written by the workflow (`scripts/med/release-notes.ts`, with the wording in `scripts/lib/med-release-notes.ts`) from the subjects of the fork's own commits since the release before: the first-parent line of `med`, sorted into New, Fixed and Changed, with tests, documentation and tooling under the fold. An upstream merge is one line, `Merged T3 Code 0.1.11`, never the commits it brings; the version is read from the merge commit's subject, so keep `Merge upstream v<version> into med`. The app shows the list above the `Full changelog` fold as `What's changed`, twelve lines at most, and nothing below it: not the lines about installing, not the checksum, and not the closing sentence that T3 Med is a personal project with no warranty and not a medical device. So a commit subject on `med` is read by the doctor: write it as a sentence about what changed. To reword a release afterwards: `gh release edit med-v2026.11.3 -R arthamegayasa/t3-med-app --notes-file notes.md`. No patient's name or data belongs in a commit subject or a release: the repository is public.
- **A release cannot be taken back** from a machine that installed it. To replace a bad release, publish the next version; deleting the bad release only stops new installs from it.
- **The workflow runs from the ref it is started on.** A pushed tag runs the workflow file of the tagged commit. A manual run needs the workflow file on the default branch (`med`).
- **The two releases made before this rule,** `med-v2026.11.1` and `med-v2026.11.2`, were built from the branch that added the workflow, before it was merged.

### Unsigned

There is no code-signing certificate. What that means for an update was read from electron-updater 6.8.9 as upstream patches it (`NsisUpdater.js`, `BaseUpdater.js`) and from electron-builder's NSIS templates:

- **Signature check.** The updater verifies the installer's publisher only when `app-update.yml` carries a `publisherName`, which electron-builder writes for a signed build. T3 Med's has none (the release check refuses one), so the step is skipped and the download is accepted on its SHA-512.
- **Integrity** therefore rests on two things: the checksums in the release's `latest.yml`, and the GitHub account that can publish to `arthamegayasa/t3-med-app`. Whoever controls that account controls what an installed T3 Med updates to, and since an update now downloads and installs without a click, within hours. The release notes carry the installer's SHA-256, and GitHub shows each file's digest.
- **SmartScreen.** The first install is a file downloaded by a browser and shows "Windows protected your PC". An update is downloaded by the app itself, which writes no mark of the web on the file (the downloaded `T3-Med-2026.11.2-x64.exe` was checked: no `Zone.Identifier` stream), and is started by the app, so SmartScreen has nothing to ask about. This was not seen on a real installation.
- **No administrator.** The installer is per-user (`%LOCALAPPDATA%\Programs\t3med`), and the updater starts it without elevation, silently: `--updated /S --force-run` from the restart button, `--updated /S` when the app is closed.
- **Install on quit.** With `autoInstallOnAppQuit` on, electron-updater starts the downloaded installer from Electron's `quit` event when the app ends with exit code 0, detached, and does nothing when the restart button already started it. Upstream's shutdown stops the backend before that event, so the installer finds no file in use. By Electron's documentation that event is not sent on Windows when the system shuts down or the user logs off, so an update is not started into a shutdown; closing T3 Med and switching the laptop off within the same half minute can still cut the installer short, and then T3 Med is reinstalled from the release page. Patient data is not in the folder the installer replaces.
- **Smart App Control,** where it is on, blocks unsigned programs whatever started them: the update would download, fail to install, and be offered again at the next start. Install the release by hand in that case, or turn Smart App Control off.

### Patient data and an update

An update, a reinstall and an uninstall never touch patient data. The data folder `~/.t3med` and Electron's profile `%APPDATA%\t3med` are outside the install folder (`%LOCALAPPDATA%\Programs\t3med`).

- An update or reinstall runs the old uninstaller with `--updated`, which removes the install folder and nothing else.
- The uninstaller deletes Electron's profile only when the installer was built with `deleteAppDataOnUninstall` or the uninstaller is started with `--delete-app-data`. `medStagePackageJson` sets `deleteAppDataOnUninstall: false` whatever upstream configures, the release check reads it back from the build, and the uninstall entry in Windows passes no such flag.
- Nothing in the installer or the uninstaller names `~/.t3med` at all.
- The updater keeps the downloaded installer in `%LOCALAPPDATA%\t3med-updater`.

### What stays closed

- **`t3 update`** fails at once with `MED_UPDATE_REFUSAL` (`apps/server/src/med/updates.ts`), which says how T3 Med updates: the desktop app by itself, with Settings > About > Check for Updates to look at once, the browser version by pulling and rebuilding the source. Nothing is looked up or written.
- **The browser version** (`start-t3-med.cmd`) runs from the source checkout and does not update itself. Its About page shows `from source` and no update button.
- **A client asking the server to update itself** (`server.updateServer` and its progress and commit calls) gets the same refusal: `server.ts` provides `layerNoSelfUpdate` in place of upstream's layer. The desktop app replaces the server with the rest of the app.
- **Server and provider updates in the web client:** the composer banners, the actions in Sharing & access, the provider update pill and `Update all` are behind `T3MED`, and the app's own update collects no server and no provider.
- **The other workflows.** Upstream's 27 workflow files stay in the tree, so merges stay clean, and are disabled in the repository's settings. A workflow file a merge adds arrives enabled: disable it (BRANDING.md, step 6).

What remains, on purpose or not yet looked at:

- `T3CODE_RELEASE_BASE_URL` still redirects the downloads `t3 update` and the server's own update would make; both are refused before they download. A managed policy's `feedUrl` is described under The feed.
- `T3CODE_DESKTOP_MOCK_UPDATES` still works in a package with no `app-update.yml`, which no T3 Med build is, and in upstream's own tests, which is why the rule is about the package and not about the variable.
- `T3CODE_DESKTOP_UPDATE_REPOSITORY` set while building changes where the web client's release links lead, not the feed.
- `T3CODE_DISABLE_AUTO_UPDATE=1` turns the updater off, as upstream's does.
- `NpmRelease` still asks the npm registry which version of upstream's `t3` package is newest. It only reports a version; nothing in T3 Med installs from npm.
- `scripts/install.sh`, `scripts/npm-launcher/` and upstream's release workflows are upstream's distribution and still name upstream. T3 Med is never installed through them.
- `MED_UPDATE_REFUSAL` set to an empty string gives upstream's update back in the CLI and the server. `MED_HIDES_UPDATE_MENU` set to `true` hides the menu's check, which matters on macOS and Linux only.
- Releases are Windows x64 only. The mobile app was not looked at: it can reach a T3 Med server and would be refused by it.
- **Seen, and not seen.** Seen on 18 November 2026 with a build of this branch made locally as `2026.11.1`, run unpacked on a temporary data folder, profile and cache: the background check found `2026.11.2` and downloaded it with no click, 211 MB in about ten seconds on that connection; the notice and the `Restart to update to 2026.11.2` button appeared; the downloaded file had the SHA-256 of that release's notes; after the app was stopped by force and started again the same file, unchanged on disk, was offered within three seconds of the check, with no new download, and with no second notice when the first run had lasted a minute and a half past its notice (stopped within 15 seconds, it repeated the notice once); and Settings > About > Check for Updates, clicked four seconds after start and so before the app's own first check, found the release. An unpacked release build counts as packaged, so its updater runs with no development switch. Not seen, because no T3 Med is installed on the machine it was built on and the test stops before the installer: the restart into the new version, the install when the app is closed, SmartScreen's silence about an update, and the menu's update check on a platform that shows a menu bar (its dialogs are tested in `apps/desktop/src/med/menu.test.ts`).
